## 0.30.0

Files on outgoing emails, and closing a ticket without a survey. **Backend dependency:** the Clokio backend with `POST /tickets/attachments`, `attachment_ids` on `POST /tickets` and `POST /tickets/{id}/replies`, and `send_survey` on `PATCH /tickets/{id}` (branch `feature/api-ticket-attachments`). On an older server the upload is a 404 and `attachment_ids` / `send_survey` are refused as unknown fields. After updating, start a NEW session and check that `clokio_whoami` reports `mcp_version` 0.30.0. Before publishing, run `node test/api-conformance.mjs` against the deployed spec: 130 tools, 136 calls.

- `clokio_create_ticket` (email, not a draft) and `clokio_reply_ticket` take `file_paths` (local files, uploaded through `POST /tickets/attachments`) and / or `attachment_ids`: up to 5 files, together within 10 MB. They go out as real attachments; the create answer names them.
- A retry with the same `idempotency_key` reuses the ids its first call uploaded (each remembered as it succeeds, until the server's `expires_at`, for the life of the process), so the server sees the same body and replays instead of refusing it; a retry after a failed upload uploads only the files still missing. When the server refuses the ids (expired, used), they are forgotten and the next retry uploads afresh. After a restart, pass the `attachment_ids` the first answer listed.
- Nothing is uploaded before the call's own checks pass: an email without a subject or body, files on a draft or on WhatsApp, and (for a reply) a ticket that is not email are refused first.
- New tool `clokio_upload_ticket_attachment` (130 tools).
- `clokio_update_ticket` takes `send_survey` (false with `state: "resolved"` closes without the satisfaction survey or rating card).
- Tests: `test/ticket-email-files.mjs`; `test/api-conformance.mjs` and `test/toolsets.mjs` updated.

## 0.26.0

Labels on an existing task (Clokio task #5874 part 1) and custom fields by option label, inside a task update and on many tasks at once (part 2), owner approved 2026-10-18. **Backend dependency:** needs the Clokio backend with task #5874 part 1 (`feature/api-task-labels-update`) and part 2 (`feature/api-custom-fields-bulk`). On an older server `PATCH /tasks/{id}` refuses the three label fields as unknown body fields (422 naming them), and `PATCH /tasks/bulk` ignores the two diff fields and, when they were the only change, answers "Provide at least one of: status, priority, due_date." After updating, start a NEW session and check that `clokio_whoami` reports `mcp_version` 0.26.0. `node test/api-conformance.mjs` now checks both tools' body keys against the spec's curated request bodies (121 tools, 127 calls).

- **`clokio_update_task` takes labels** - `label_names` REPLACES the task's whole label set (an empty list removes every label); `add_label_names` / `remove_label_names` change it, keeping the rest. A name that does not exist in the organisation is CREATED, exactly as on `clokio_create_task`; names match case-insensitively; a remove never creates; adding a label the task carries or removing one it does not carry changes nothing. Each real change is written to the task's activity log (credited like any other edit) and the answer is the updated task with its labels. An empty add or remove list is not a change and is not sent; a call left with nothing to change is refused before any request. `label_names` together with a non-empty diff field is refused before any request; the same name (trimmed, case-insensitive) in both diff lists is refused before any request, and the server also refuses collation variants of an existing label ("Café" and "Cafe" count as one).
- **`clokio_bulk_update_tasks` takes `add_label_names` / `remove_label_names`** - alone or beside status / priority / due_date, which are now "at least one of" five (an empty list does not count; refused before any request when none is given). A missing name is created once for the whole batch, before any task changes. A task in `invalid_status` is skipped whole, its labels included. The answer is still `{updated, not_found, invalid_status}`, plus `labels_failed` when labels were sent: the ids whose label change could not be written after their other changes were saved (normally empty). Replacing a whole set is `clokio_update_task`'s `label_names`; the bulk tool has no such field.
- **Label names are at most 50 characters** (the Clokio column's width), on `clokio_create_task` too (it allowed 100; the server's new rule refuses 51 or more, where it used to fail with a 500). Up to 50 names per field on update and bulk.
- **An option by its label** - `clokio_set_task_custom_field` (and every custom field write below) accepts a dropdown or multi-select option's LABEL as shown on screen as well as its stored value: value first, then the exact label, then the label ignoring case and surrounding spaces. A label two options share is refused asking for the value; an unknown one is refused naming the field and listing its options. The tool now also takes `value: null` (clears the answer) and `actor_employee_code` (the server logs a `custom_field_changed` activity row; omitted, CLOKIO_DEFAULT_ACTOR or the key issuer is credited).
- **`clokio_update_task` takes `custom_fields`** - an object of field_key -> value, written in the same request as the other fields. Every field is checked before anything is written: one bad field refuses the whole update and nothing changes.
- **New: `clokio_bulk_set_task_custom_field`** - `ids` (1-200) and `custom_fields` (1-50 fields) over `PATCH /tasks/bulk/custom-fields`. Partial success, passed through as the server answers: `{updated, not_found, field_not_on_project, invalid_value, moved, errors}`; `moved` lists tasks that moved to another project while the request ran (nothing written, retry them) (fields are per project; per task it is all or nothing). Registered in the `tasks` toolset; 121 tools by default.

**Part 2 on an older server:** `custom_fields` on `clokio_update_task` is refused as an unknown key (422), a label is refused as "not an option", and `clokio_bulk_set_task_custom_field` answers 404 (or 405).

## 0.25.0

From the QA notes on 0.22.1 + 0.23.0 (Clokio task #5808, "New small notes" N1-N4), plus #5 (a new outbound ticket) and #9 (smaller ticket gaps).

**Backend dependency:** needs the Clokio backend released with the 0.25 API (`feature/mcp-0.25-api`). On an older server the new routes (`POST /tickets`, `POST /ticket-labels`, `POST /contacts`, `GET /inboxes/{id}/whatsapp-templates`) answer 404 (or 405), the new `clokio_list_tickets` filters are refused as unknown parameters (422), and a replay is not marked. After updating, start a NEW session and check that `clokio_whoami` reports `mcp_version` 0.25.0. `node test/api-conformance.mjs` checks 120 tools (126 calls) against the deployed spec.

- **A 404 in the server's own words (E7, N1)** - the 0.25 API names a missing, other organisation's or invisible project (one the acting employee cannot see; a visible project without create rights stays 403) on `POST /tickets/{id}/tasks` ("That project is not available.") and a draft that is not on the ticket or was already deleted on `DELETE /tickets/{id}/drafts/{messageId}` ("This draft no longer exists."). `clokio_create_task_from_ticket` and `clokio_delete_reply_draft` show those sentences as they come. Only a plain "Not found." (the ticket is missing or the acting employee cannot open it) adds that, and names an older server as ONE possible cause. The follow-up reads of part 1 (`with404Cause`, up to 21 extra GETs) are gone.
- **A replay says so (E7, N4)** - the server marks a replayed idempotent answer (header `Idempotency-Replayed: true`, and `data.replayed: true`). `clokio_create_task_from_ticket` then answers "Task #N was already created from this ticket (replayed, no new task)"; `clokio_create_ticket` answers that the ticket was already created and nothing was sent again; `clokio_reply_ticket` adds a `replayed_note` that nothing new was sent.
- **`clokio_reply_ticket` takes `idempotency_key`** - optional; without it every call still gets a fresh key (a second call is a second reply). To retry safely after a timeout or a lost answer, pass the SAME key with the same fields within 24 hours: the first answer is replayed and nothing is sent twice. The answer returns the key used (`idempotency_key`).
- **An empty time-entry list claims no time zone (N2)** - `clokio_list_time_entries` with no entries answers "No time entries." and that `clokio_update_time_entry` takes the person's local date and times, instead of the UTC header an older server gets.
- **New name: `clokio_get_leave_days_taken` (N3)** - the tool returns days taken, not balances, so it has that name. `clokio_get_leave_balances` stays as a deprecated alias with the same input and answer; its description starts with "DEPRECATED: use clokio_get_leave_days_taken".
- **New: `clokio_create_ticket` (#5)** - opens a new ticket and sends its first message, as "New email" / "New WhatsApp message" on the Tickets screen, as the acting employee. Email: `inbox_id`, `to` (1-20), `cc` / `bcc`, `subject`, `body` (Markdown, converted to HTML). WhatsApp: `inbox_id`, `to` (one number with its country code) and `template` (`name`, `language`, `params` as a list or a map, `header_text`, `buttons`); a customer's open ticket on that number is reused, and the answer says so. Optional `contact_id`, `assignee_employee_code` and `draft` (default false). Needs `tickets:write`, plus `tickets:send` to send; a new address or number needs the acting employee's `tickets.manage`; at most 10 new tickets per 10 minutes per key, counting only successful creates (a refused one uses nothing), and a replay of a stored answer is answered even past the limit. `draft: true` creates the ticket with a pending draft and sends nothing: a person opens it in Clokio and clicks "Use this draft". On an email draft ticket, the first reply (from Clokio, or `clokio_reply_ticket` without `recipients`) goes to the drafted To/Cc/Bcc with the drafted subject, and the draft then reads "used" (it can no longer be deleted); `clokio_reply_ticket` and `clokio_delete_reply_draft` say so. Every call sends an `Idempotency-Key` (a fresh UUID, or `idempotency_key` to retry), returned in the answer. A field of the other channel, or a missing subject, body, template or recipient, is refused before any request. Marked destructive: a send reaches a customer.
- **New: `clokio_list_whatsapp_templates`** - the approved templates of one WhatsApp number (`GET /inboxes/{id}/whatsapp-templates`, `tickets:read`), with the slots to fill `template` on `clokio_create_ticket`: name and language, `params` (a list in order for a numbered template, a map by name for a named one), `header_text` when the header has a variable, and `buttons[index]` for a button that needs a URL suffix (with the `url_prefix` it is appended to) or a code. A template the API cannot send (for example a media header) is marked NOT SENDABLE with the server's reason. `clokio_create_ticket` and the WhatsApp part of `clokio_reply_ticket` point at it (the reply sends free text only; after the 24-hour window, a template goes through `clokio_create_ticket`, which reuses the customer's open ticket on that number).
- **`clokio_list_tickets` filters and sort (#9)** - `label_ids` (any of 1-20 labels), `created_after` / `created_before` (exclusive; without an offset in the organisation's time zone), `needs_reply` (true: the customer spoke last) and `sort` (`updated_desc` default, `updated_asc`, `created_desc`, `created_asc`). The cursor encodes its sort: the next-page line names the sort to pass with it.
- **New: `clokio_create_ticket_label` (#9)** - `name` (one line, max 40, unique) and `color` (`#rrggbb`); needs `tickets:write` and the acting employee's `tickets.manage`. The answer names the new `label_id`.
- **New: `clokio_create_contact` (#9)** - `name` with an `email` and / or a `phone`; needs `tickets:write` and `tickets.manage`. Never a merge: an address or number that a contact you can see holds is a 409, and the answer prints that contact's id and suggests `clokio_get_contact`.

One zone on the page is named once in the header; a page that mixes zones names it on each row. `clokio_update_time_entry` and `clokio_delete_time_entry` print the same local line with its zone; `clokio_log_time`, `clokio_start_timer`, `clokio_stop_timer` and `clokio_get_active_timer` keep the API's object and add `entry_line` first; a refused start (409) names the running entry the same way. - **New: `clokio_delete_reply_draft`** - delete one of your own reply drafts that nobody has used (`DELETE /tickets/{id}/drafts/{messageId}`, `tickets:write`, no `tickets.manage`, owner decision D3). Marked destructive. The server's refusals come back in its own words: not on this ticket (404), not a reply draft or already used (422), someone else's draft (403). `clokio_create_reply_draft` now names it in its answer. (#2a)
- **New: `clokio_list_ticket_tasks`** - the tasks opened from a ticket that the acting employee may see, one line each (`GET /tickets/{id}/tasks`, needs both `tickets:read` and `tasks:read`). (#4)

- **Days taken in `clokio_get_leave_balances`** - the answer lists, per leave type, `taken` (approved) and `pending` days for the year, half days as 0.5, with an optional `year` (2000-2100, default the employee's current year). ### Needs no new backend

- **Message ids** - `clokio_get_ticket` and `clokio_list_ticket_messages` print `message #<id>` on every message, `REPLY DRAFT (pending)` lines included, so a draft or a message can be named. (#2b)
- **`clokio_create_reply_draft` on a resolved or spam ticket** - the tool reads the ticket's state first. On a resolved or spam ticket the draft is still saved, and the answer adds a warning: the draft will not appear in the open queue, and `clokio_update_ticket state=open` reopens the ticket if a person should pick it up. The ticket is never reopened automatically (owner decision D2). If the state cannot be read, the draft is saved without the warning. The answer now writes the draft as `message #<id>`. (#2c)
- **A colleague's name is no longer wrapped as untrusted** - in ticket threads an identified employee (author type employee with an employee_code) is printed as `Dana (00031)`; contacts, bots, the WhatsApp Business app and unknown authors stay inside `<untrusted_customer_content>`. A wrapper tag inside a colleague's name is still defused. (#3)
- **`clokio_get_inbox` shows tickets** - with the tickets toolset loaded, and when `employee_code` is the key's acting employee (`acting_as` from `/me`, else `issued_by`), the answer gains a `tickets` part: the open tickets assigned to that person (`GET /tickets?assignee=me&state=open`, one wrapped line each, first 50, the next cursor named) and which of them wait for our reply (`waiting_for_reply`, from `waiting_since`). For any other employee `tickets` only says why none are shown (ticket visibility is the acting employee's), and a failed tickets read is reported there without failing the task inbox. Without the tickets toolset nothing changes and no extra call is made. A "waiting for me" filter on the server (#9c) would make this exact; until then it lists what is assigned and open. (#9e)
- **`employee_code` on the leave and time-entry tools** - `clokio_list_leaves`, `clokio_get_leave_balances` and `clokio_list_time_entries` take `employee_code`, like every other tool, and still accept `employee` (the old name) as an alias. Both with different values is refused before any request. The descriptions now name the real parameters; the API query parameter is unchanged. (L2)
- **The 92-day limit** - `clokio_list_leaves` and `clokio_list_time_entries` say that `to - from` may be at most 92 days, and refuse a longer range before the request with the server's sentence ("Date range cannot exceed 92 days.") and a hint to split it. The tool does not split the range itself: leave rows carry no id, so a leave that crosses two windows could not be told apart. (L3)
